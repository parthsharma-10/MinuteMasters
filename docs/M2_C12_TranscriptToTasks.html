Section 2: Prompt and Solution Design

(a) Solution Design Overview

1. What problem, for whom?
In student clubs, software project teams, and campus committees, meeting discussions are fast and unstructured. Notes are taken late or incompletely, causing action items and owners to be forgotten. Jabra’s 2026 global workplace research (conducted across multiple countries including India) reveals that 58% of meeting time is perceived as unproductive, 59% of meetings require a follow-up meeting, and 91% of workers who dread meetings leave with unclear action items (Source). Our solution is designed for student club leads, engineering project teams running agile standups, and academic committees needing clear, auditable minutes without tedious manual effort.

2. Input and Output:
Input: Unstructured meeting transcripts containing messy speech, interruptions, and informal temporal references.
Output: Validated RFC 8259 JSON and an audit-ready Markdown table of decisions and action items. Every action item contains: concrete task, explicit owner (or "not stated"), explicit deadline (or "not stated"), and an exact supporting verbatim transcript quotation.

3. How many prompts/steps and why?
We employ a Two-Stage Decoupled Pipeline (2 Prompts):

  • Prompt P1 (Candidate Extraction): Focuses on high recall, extracting candidate decisions and tasks with verbatim evidence quotes and fallback rules.
  • Prompt P2 (Adversarial Verification):** Operates as an independent fact-checker. It receives the original transcript and P1's candidate JSON, verifies that evidence quotes are word-for-word accurate, confirms speaker consent, validates deadlines, prunes hallucinated proposals, and outputs clean verified deliverables.
Why 2 steps? In Milestone 1, single-step prompts suffered from confirmation bias: models hallucinated owners on unassigned tasks (38% error rate) and defended their fabrications. Decoupling extraction from verification reduced owner hallucination to 0%.

4. Which tool/model and why?
We use Gemini 2.5 Flash in Google AI Studio, orchestrating with a Python 3.11 backend and Streamlit web UI, accompanied by an offline Smart Heuristic Grounding Engine. Gemini 2.5 Flash offers a massive context window (ideal for multi-hour transcripts), near-zero inference cost (~$0.0003 per meeting), rapid sub-second latency, and strict JSON compliance. In our prototype, we engineered a hybrid architecture: evaluators can input a Google Gemini API key for live LLM inference or test any custom transcript offline without an API key using the smart dynamic parser.

5. What changed since Milestone 1?
Transitioned from a single zero-shot text prompt (v1) to a two-stage decoupled pipeline (P1 + P2); enforced strict JSON schema with mandatory evidence_quote citations; introduced deterministic "not stated" fallback constraints (incorporating feedback from senior mentor Ojas Vats); lowered sampling temperatures to 0.2 and 0.1; built an interactive Streamlit prototype supporting live API execution and offline parsing on any custom transcript, complete with 1-click JSON and CSV export.

Tool & ModelGoogle AI Studio / Gemini 2.5 Flash

System Prompt 
You are the MinuteMasters Core Extraction Engine. Your task is to extract all finalized decisions and actionable tasks from spoken meeting transcripts with zero hallucination.
Rules:
1. Every item must include an exact verbatim evidence_quote from the transcript.
2. If owner is not explicitly committed, write "not stated". NEVER guess.
3. If deadline is not explicitly stated, write "not stated".
4. Only extract genuine consensus decisions; skip casual ideas or discarded proposals.
5. Respond ONLY with a valid JSON object matching the requested schema.

Section 3: Implementation

1. What is Built

MinuteMasters has implemented a complete, modular meeting intelligence pipeline comprising:

  • Core Two-Stage Pipeline: Decoupled extraction (P1) and adversarial verification (P2) implemented in code/transcript_pipeline.py.
  • Interactive Web Prototype: A Streamlit application (code/app.py) enabling real-time transcript analysis, model selection, temperature control, and CSV export.
  • Jupyter / Colab Prototype: Executable notebook (code/TranscriptToTasks_Prototype.ipynb) with saved outputs.
  • Benchmark Suite: 12 hand-crafted evaluation transcripts in test-data/ evaluating normal, edge, and invalid inputs.

2. Module Status Table

Module Name What It Does Status Notes
Module 1: Transcript Ingestion & Pre-processor Sanitizes raw text, removes disfluencies, normalizes speaker tags, checks token length. Working Fully integrated in Streamlit app and Python orchestrator.
Module 2: Structured Extractor (P1) Executes Prompt P1 via live Gemini 2.5 Flash API or smart local parser to extract decisions and tasks with verbatim quotes. Working Supports both live cloud LLM API calls and offline dynamic parsing on any custom transcript.
Module 3: Verification Engine (P2) Audits candidate JSON against transcript, enforces owner consent, removes hallucinations. Working Zero hallucinations on all 12 benchmark test runs.
Module 4: Export & Markdown Formatter Renders clean Markdown checklist and RFC 8259 JSON, with 1-click JSON and CSV export downloads. Working Integrated into UI; supports 1-click JSON and CSV file downloads.
Module 5: Multilingual Code-Switching Normalizer Normalizes Hindi/Hinglish temporal words ('kal shaam') to standard dates. Partly working Extracts tasks/owners, but temporal date parsing fails (Test 11). M3 target.
Module 6: Jira / Slack Webhook Integration Automatically pushes verified action items into Jira tickets and Slack channels. Not started Scheduled for Milestone 3 implementation.

2. Known Limitations & What We Will Try Next (Milestone 3 Roadmap)

  1. Code-Switched Temporal Normalization (Test 11): Hindi colloquialisms ("kal shaam", "parson") remain un-normalized. We will add a dedicated pre-processing normalizer prompt mapping colloquial phrases to ISO calendar dates.
  2. Document Type Guardrail (Test 12): Non-meeting academic notes were force-fit into tasks. We will introduce a lightweight P0_CLASSIFIER prompt that validates transcript structure before extraction.
  3. Multi-Hour Long Transcripts: For recordings > 45 minutes, we will implement a sliding-window chunking strategy with speaker buffer preservation.
  4. Direct Webhook Integrations: Exporting currently requires copy-pasting. We will build direct API webhooks for Jira Cloud and Slack.
